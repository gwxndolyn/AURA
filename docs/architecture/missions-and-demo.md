## Mission engine

A **mission** is an objective that becomes a validated, dependency-ordered plan
(`MissionPlan` + `MissionTask` rows) and is executed one bounded step at a time.

| Piece | File | Notes |
|---|---|---|
| State machines | `state.ts` | Mission: DRAFT → PLANNING → AWAITING_APPROVAL → READY → RUNNING ⇄ PAUSED → COMPLETED/FAILED/CANCELLED. Task transitions include the bounded repair loop. |
| Graph | `graph.ts` | cycle / unknown-dependency detection, eligibility, failure propagation, levels. |
| Planner | `planner.ts` | Plans composed by risk from task requirements; agents assigned by capability. Rejects cycles, out-of-allowlist tools, self-review, missing TEST/REVIEW for a code change, concurrent writers of one file. |
| Engine | `engine.ts` | `advanceMission` claims ≤1 task with a lease + file locks, recovers expired leases, applies outcomes and the bounded repair loop. |
| Executor | `executor.ts` | One attempt = one `MissionTaskRun`: context, budget check before each model call, tools, validated output, handoff. |
| Report | `report.ts` | Built only from persisted rows. Ledger keeps **proposed / executed / verified / human-approved / deployed** apart (deployed is always 0 — missions never deploy). |

Execution model: no background timers. The mission page (or any client) calls
`POST …/missions/:id/advance` repeatedly; state lives in the DB, so a refresh
resumes. Concurrent callers are safe — the losing caller gets
`note: "task claimed by another worker"` and the UI retries.

### Showcase: checkout fix (`template = "checkout-fix"`)

A bundled module (`fixtures.ts`) with a real float-rounding bug and five tests.
Tasks (HIGH risk): requirements → architecture ∥ reproduce (real `node --test`
in Docker) → fix (round N applies repair candidate N; with no API key these are **prepared candidates**,
labelled as such) → verify (on failure, sends a BUG_REPORT and reopens fix,
max 3) → payment-safety review (deterministic checks on the final code) →
approval gate → report. Without Docker, reproduce fails as **UNVERIFIED** and
the mission fails — it never pretends tests ran.

Approval gates store a sha256 of the exact code. `decideApproval` re-hashes
the current code; if it changed, the approval is cancelled. Gate decisions
need **ADMIN**; plan decisions need **MEMBER**; both are attributed to the
authenticated user. Agents have no route to either.

Other objectives get a generic analysis plan with no code tasks (AURA has no
executable codebase for them) — stated in the plan's risks.

### API

| Route | Role | Purpose |
|---|---|---|
| `GET/POST companies/[id]/missions` | VIEWER / MEMBER | list; create (+plan) |
| `POST …/missions/example` | MEMBER | create the user's own showcase mission (source `EXAMPLE`) |
| `GET …/missions/[missionId]` | VIEWER | detail (payload hash never returned) |
| `POST …/[missionId]/plan` | MEMBER | `approve` / `reject` / `replan` |
| `POST …/[missionId]/advance` | MEMBER | 1–5 bounded steps |
| `POST …/[missionId]/cancel` | MEMBER | stop scheduling |
| `POST …/[missionId]/approvals/[approvalId]` | ADMIN | decide a gate (IDOR-scoped to mission + workspace) |
| `GET …/[missionId]/report` | VIEWER | completion report |

## Demo workspace

- `POST /api/demo` (signed-in users only) returns the caller's **own** demo
  workspace (`isDemo = true`, owned by them), creating it on first use. There is
  no shared demo account; the old `ensureUser()` / `founder@aura.local` path was removed.
- The baseline is generated by **running the real engines**: 3 simulated days,
  four missions (completed, paused at the gate, awaiting plan approval,
  cancelled), a simulated staging release, a cyber-range exercise, and an agent
  evaluation. Plan approvals during setup are attributed to `demo-setup`; **no
  gate is pre-approved**. Baseline missions are then marked `SEEDED` and are
  read-only (`assertMutable` in the engine → 409).
- `POST companies/[id]/demo/reset` — OWNER only, demo workspaces only, body
  `{ "confirm": "RESET" }`. A lease on `Company.demoLockUntil` refuses concurrent
  resets (409). One transaction deletes this company's rows model by model
  (every statement filtered by `companyId`) and re-provisions agents/infra via
  `provisionWorkspace`; then the baseline is regenerated. Each baseline step
  reports ok/failed — a partial failure is shown, not hidden. Audit log and
  memberships are kept.

## Onboarding & tour

- `User.onboarding` (JSON) holds `{ introSeenAt, skippedAt, completedAt, steps[] }`.
- `GET/POST /api/onboarding` — actions `step`, `intro-seen`, `skip`, `restart`.
  Optional `companyId` writes a `TOUR_PROGRESS` audit row containing only the
  step id (access-checked). No mission content is ever sent.
- UI: `components/onboarding/tour.tsx` — 3-card skippable intro on first visit,
  checklist + glossary panel from the topbar help button, ⌘K "Open the product
  tour", or Settings → Help. Glossary terms (`lib/glossary.ts`) render through
  `components/ui/term.tsx` (hover/focus tooltip, no library).

## Instrumentation

Mission events carry `meta.analytics` keys (`mission_created`, `plan_generated`,
`plan_approved`, `mission_completed`, `mission_failed`, `demo_reset`) through
`emitEvent`; human decisions and resets are in the audit log.
